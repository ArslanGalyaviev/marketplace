# Marketplace

Небольшой учебный проект по проектированию архитектуры маркетплейса.

## Архитектура

Для проекта выбрана микросервисная архитектура.

Основные сервисы:

* Users Service
* Products Service
* Orders Service
* Payments Service
* Notifications Service
* Feed Service

Для обычных запросов между сервисами используется HTTP.

Для асинхронного взаимодействия используется Kafka.

В архитектуре у каждого сервиса предполагается своя база данных.

## C4 диаграмма

Диаграмма находится в папке `docs`:

* `c4-container.puml` — исходник диаграммы
* `marketplace-c4-container.png` — готовая картинка

На диаграмме показаны пользователи, сервисы, базы данных и основные взаимодействия между ними.

## Домены и ответственность

### Users

Работа с пользователями, профилями и ролями.

### Products

Работа с товарами, ценами и остатками.

### Orders

Создание и хранение заказов, а также изменение их статусов.

### Payments

Создание платежей и хранение их статусов.

### Notifications

Отправка уведомлений о событиях заказа.

### Feed

Формирование ленты товаров и хранение истории взаимодействий пользователей с товарами.

## Распределение доменов по сервисам

Каждый основной домен выделен в отдельный сервис.

Такое разделение позволяет каждому сервису отвечать за свою часть системы и не зависеть напрямую от базы данных другого сервиса.

Например, Products Service работает с товарами, а Users Service отвечает за пользователей. Если Products Service нужно проверить продавца, он обращается к Users Service через API.

## Владение данными

Каждый сервис владеет своими данными.

| Сервис                | Данные                               |
| --------------------- | ------------------------------------ |
| Users Service         | пользователи, профили и роли         |
| Products Service      | товары, цены и остатки               |
| Orders Service        | заказы                               |
| Payments Service      | платежи и их статусы                 |
| Notifications Service | уведомления                          |
| Feed Service          | история взаимодействий пользователей |

Общая база данных между сервисами не используется.

## Взаимодействие между сервисами

### Синхронное взаимодействие

Для запросов, где нужен ответ от другого сервиса, используется HTTP.

Основные примеры:

```text
Products Service -> Users Service
Orders Service -> Users Service
Orders Service -> Products Service
Orders Service -> Payments Service
Feed Service -> Users Service
Feed Service -> Products Service
```

Например, Orders Service обращается к Users Service, чтобы проверить пользователя.

### Асинхронное взаимодействие

Для событий используется Kafka.

Основные примеры:

```text
Products Service -> Kafka -> Feed Service

Payments Service -> Kafka -> Orders Service

Orders Service -> Kafka -> Notifications Service
```

Такой подход позволяет сервисам обмениваться событиями без постоянного прямого вызова друг друга.

## Альтернативные варианты архитектуры

Перед выбором микросервисной архитектуры можно рассмотреть несколько вариантов.

### Вариант 1 — монолит

Все функции маркетплейса находятся в одном приложении и используют одну базу данных.

Плюсы:

* проще разработка;
* проще запуск;
* меньше сетевого взаимодействия.

Минусы:

* сложнее независимо масштабировать отдельные части;
* изменения в одном месте могут затрагивать всё приложение;
* общая база данных создаёт сильную связанность.

### Вариант 2 — микросервисы

Функции маркетплейса разделены на отдельные сервисы: Users, Products, Orders, Payments, Notifications и Feed.

У каждого сервиса своя база данных. Для синхронных запросов используется HTTP, для событий — Kafka.

Плюсы:

* понятные границы ответственности;
* сервисы можно изменять независимо;
* каждый сервис владеет своими данными.

Минусы:

* сложнее разработка и запуск;
* больше сетевого взаимодействия;
* нужно отдельно следить за несколькими сервисами.

## Выбор архитектуры

В качестве итогового варианта выбрана микросервисная архитектура.

Она подходит для данного кейса, так как в маркетплейсе есть несколько отдельных доменов: пользователи, товары, заказы, платежи и уведомления.

При этом каждый сервис может отвечать за свои данные.

По сравнению с монолитом такой вариант сложнее в разработке и запуске, но лучше показывает границы ответственности между основными частями маркетплейса.

## Users Service

В рамках домашней работы был реализован Users Service.

Сейчас сервис содержит только endpoint для проверки работы:

```text
GET /health
```

Ответ:

```json
{"status": "ok"}
```

Бизнес-логика в сервисе не реализована.

## Запуск

Перейти в папку сервиса:

```bash
cd users-service
```

Собрать Docker-образ:

```bash
docker compose build
```

Запустить сервис:

```bash
docker compose up
```

Проверить health-check в другом терминале:

```bash
curl http://localhost:8000/health
```

Ожидаемый ответ:

```json
{"status": "ok"}
```

Остановить сервис:

```bash
docker compose down
```
